# Памятка участнику 3: вход CDM

> Эта памятка фиксирует исходный контракт и тестовый эталон DDS. CDM и Metabase уже реализованы; актуальный словарь графиков и результат новой полной загрузки на Mac приведены в [CDM_METRICS.md](CDM_METRICS.md) и [CDM_WORKLOG.md](CDM_WORKLOG.md). Указанные ниже 993 Issues относятся только к прежнему volume на другом компьютере и не являются ожидаемым числом для новой выгрузки.

Здесь собраны входы CDM и ожидаемые результаты. Окончательное зерно CDM, витрины, дашборды и роль Metabase выбирает и реализует участник 3. Подключение DDS к DAG выполняет участник 1. Подробности загрузчика описаны в [контракте DDS](DDS_CONTRACT.md); для CDM они не нужны.

## Что читать

CDM читает только схему `dds`, без STG:

- `dds.publication_manifest` — что опубликовано и можно ли этим пользоваться. Одна строка на репозиторий: текущий запуск, исходная партия, версия правил, граница когорты, горизонт отчётности, `last_complete_report_day` и `ready_for_cdm`.
- `dds.issues`, `dds.issue_status_versions`, `dds.issue_events` — задачи, интервалы статуса SCD2, события с признаками фактических переходов.
- `dds.issue_current_labels`, `dds.issue_current_assignees`, `dds.labels`, `dds.users` — текущий срез меток, исполнителей и справочники.
- `dds.report_day_end(day, repository_ids)` и `dds.report_cutoff(at, repository_ids)` — проверка допустимого исторического среза. При неполном или будущем дне функции завершаются ошибкой.

Правила чтения:

- Данные и манифест читаются **одной транзакцией** `REPEATABLE READ READ ONLY`.
- Используются только репозитории с `ready_for_cdm=true`. Итоговому CDM нужны все три репозитория: в манифесте должны быть три строки и все с `ready_for_cdm=true`. В результате `load`/`validate` полноту набора показывает `coverage_complete`.
- Передаваемый набор закрепляется парами «репозиторий — исходная партия» из манифеста, а не одним общим `run_id`: репозитории могут публиковаться разными запусками.
- Горизонт отчётности у проектов разный. Для сравнения проектов берётся минимальный, поэтому передавайте функции все сравниваемые `repository_id`.

## Нормативные правила показателей

Все календарные границы задаются в UTC. «Конец дня D» — состояние непосредственно перед следующей полуночью: переход ровно в полночь относится к следующему дню. Срез: `cutoff = dds.report_day_end(D, ids)`.

| Показатель | Нормативное правило |
|---|---|
| Новые задачи | Уникальные задачи по дате создания: `count(DISTINCT issue_id)` по UTC-дате `created_at` |
| Доля закрытых | Закрытые на конец дня / все задачи когорты, созданные к этому моменту (`created_at < cutoff`) |
| Открытые задачи | Исторический статус из SCD2 на конец дня: `valid_from < cutoff AND (valid_to IS NULL OR valid_to >= cutoff)` |
| Время первого закрытия | Медиана индивидуальных сроков среди впервые закрытых к срезу. Первое закрытие — первое событие с `is_status_transition AND status_after='closed'`, конверсия в Discussion тоже считается |
| Повторные открытия | Когда-либо повторно открытые / когда-либо закрытые к одному срезу. Учитываются только фактические переходы (`is_status_transition`), а не наличие типа `reopened` |
| Текущие метки | Уникальные задачи внутри каждой метки выбранного текущего снимка |

Дополнительно:

- **Медиана.** Основная медиана накопительная: все задачи, впервые закрытые до среза. Медиана задач, впервые закрытых внутри месяца, — отдельный показатель. Медианы групп не объединяются усреднением, общая медиана считается по индивидуальным срокам.
- **Доли.** Общие доли считаются из суммарных числителей и знаменателей, а не как среднее долей. При нулевом знаменателе результат отсутствует (`NULL`), а не равен нулю.
- **Автор.** Фильтр по автору — `author_id`. Задачи без автора (`author_id IS NULL`, удалённый пользователь) остаются в общей численности.
- **Текущий срез.** Метки и исполнители относятся к текущему срезу. Не выдавайте их за историческое состояние на прошлую дату. Несколько меток или исполнителей у задачи не должны размножать задачи: считайте `count(DISTINCT issue_id)` и не соединяйте метки с исполнителями в одном запросе.
- **Последний интервал.** `valid_to IS NULL` — последний известный статус, а не прогноз после горизонта.

Эталонные запросы шести показателей: [CDM_REFERENCE_METRICS.sql](sql/CDM_REFERENCE_METRICS.sql). Это определения для сверки, а не готовые витрины.

## Тестовый DDS и контрольные результаты

Небольшой воспроизводимый DDS создаётся только в отдельной базе с именем на `_test`. Защита сравнивает её адрес с рабочим `DWH_DB_*` до подключения. Запрет публикации `sample` в рабочей базе не меняется: синтетические партии помечены как полные только внутри тестовой базы. Не используйте для этого базу интеграционных тестов DDS: тестовый DDS занимает имена трёх репозиториев.

```bash
docker compose exec analytics-db createdb -U analytics github_issues_cdm_test
docker compose run --rm --no-deps -e DDS_TEST_DSN='postgresql://analytics:<пароль>@analytics-db:5432/github_issues_cdm_test' airflow-scheduler python -m src.dds.fixture
docker compose exec -T analytics-db psql -U analytics -d github_issues_cdm_test -f - < docs/sql/CDM_REFERENCE_METRICS.sql
```

Набор содержит 9 задач в трёх репозиториях. В нём есть:

- задача без автора;
- задача с двумя метками и двумя исполнителями, задача с тремя исполнителями;
- повторное открытие, закрытие и открытие в одну секунду;
- закрытие ровно в полночь после отчётного дня;
- задачи, созданные после отчётного дня.

Контрольные результаты на конец дня 2023-03-31, месяц — март 2023:

| Показатель | Kotlin/kotlinx.coroutines | ktorio/ktor | android/nowinandroid | Всего |
|---|---:|---:|---:|---:|
| Новые задачи за март | 2 (01.03, 20.03) | 1 (31.03) | 1 (31.03) | 4 |
| Создано к срезу | 4 | 2 | 2 | 8 |
| Закрыто / открыто на конец дня | 2 / 2 | 0 / 2 | 0 / 2 | 2 / 6 |
| Доля закрытых | 0,5000 | 0,0000 | 0,0000 | 0,2500 |
| Медиана первого закрытия, накопительная, дней | 10 (3 задачи) | — (0) | 10 (1) | 10 (4) |
| Медиана первого закрытия за март, дней | 20 (2) | — (0) | — (0) | 20 (2) |
| Повторно открытые / когда-либо закрытые | 1 / 3 = 0,3333 | 0 / 0 = — | 1 / 1 = 1,0000 | 2 / 4 = 0,5000 |
| Текущие метки, задач | bug 2, feature 1, help 1 | bug 2, feature 1 | ui 1 | — |

На этих данных видно:

- средняя доля закрытых по проектам (0,1667) не равна общей (0,2500);
- накопительная медиана (10) отличается от месячной (20);
- у Ktor знаменатель повторных открытий нулевой, поэтому результат отсутствует.

Ещё две контрольные величины:

- к срезу создано 8 задач, у 7 известен автор; фильтр `author_id` пользователя `alice` даёт 2;
- связей с исполнителями 6, а различных задач с исполнителями 3.

Сумма по меткам (8) не равна числу задач с метками (6).

Эти значения проверяет интеграционный тест `test_reference_fixture_reproduces_control_metrics`.

## Чего тестовый набор не заменяет

Тестовый DDS проверяет логику, а не полноту данных. Итоговая приёмка выполняется на рабочем volume с 993 задачами по процедуре из [контракта DDS](DDS_CONTRACT.md#проверки-запросы-и-тестовый-dds).
