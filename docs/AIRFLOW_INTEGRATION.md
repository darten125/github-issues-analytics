# Подключение DDS и CDM к Airflow после готовности их кода

> Историческая памятка о точке интеграции. Актуальный DAG уже содержит задачи `publish_dds` и `publish_cdm`; команды и порядок запуска приведены в [README](../README.md), а правила витрин — в [словаре CDM](CDM_METRICS.md).

Этот документ описывает точки интеграции. Существующий DAG и Compose в рамках передачи **не изменяются**; задач DDS/CDM в Airflow пока нет. Полный контракт источника описан в [STG_DDS_CONTRACT.md](STG_DDS_CONTRACT.md). Код DDS и вызываемый адаптер `src.dds.airflow_adapter.run_from_stg_summary(summary)` уже готовы; их интерфейсы описаны в [DDS_CONTRACT.md](DDS_CONTRACT.md).

## Текущая цепочка STG

`github_issues_stg` запускается только вручную (`schedule=None`, `catchup=False`), с `LocalExecutor`, `max_active_runs=1` и `max_active_tasks=1`. Порядок задач:

```text
validate_run → check_resources → prepare_stg_schema
    → load_kotlin → verify_kotlin
    → load_ktor → verify_ktor
    → load_nowinandroid → verify_nowinandroid
    → summarize
```

`repository=all` обрабатывает все три репозитория последовательно. При выборе одного репозитория другие `load_*`/`verify_*` возвращают `None` без GitHub-запросов; `summarize` возвращает только выбранный репозиторий. `validate_run` проверяет `full_load=true` вместе с `max_issues=null`; `prepare_stg_schema` применяет миграции STG; `verify_*` читает сохранённую партию PostgreSQL, а не только статус HTTP-цикла.

Результат каждого `verify_*` содержит `repository`, `batch_id`, `status`, `issue_scan_status`, `issue_scan_passes`, `issue_scan_issue_count`, `issues_selected`, `events_fetched`, `issue_versions_inserted`, `event_versions_inserted` и `created_since`. `verify_*` завершается ошибкой, если партия не записала (`recorded`) ту границу, которая задана параметром запуска. `summarize` возвращает словарь `{"status":"succeeded","mode":...,"full_load":...,"batches":[...]}`. В этих XCom нет `raw_json`, токена или паролей. `batch_id` следует передавать будущему DDS через этот результат и заново сверять с БД.

## Условие запуска STG → DDS

Будущая задача DDS должна зависеть от `summarize`, а не от одного `load_*`. Для промышленного набора она проверяет `full_load=true`, ожидаемые репозитории и каждый переданный `batch_id` по `stg.load_batches`:

1. `status='succeeded'`, `issue_scan_status='verified'`, `issue_scan_passes>=2`.
2. `issue_scan_issue_count` соответствует проверенному числу уникальных Issue ID этой партии. `issues_fetched` и число JSON-снимков не заменяют этот показатель.
3. Для переданного `batch_id` нет строк `stg.issue_event_loads` со статусом `running` или `failed`.
4. Для каждого Issue, входящего в подтверждённый репозиторий, существует успешный полный обход `/events` — он может принадлежать прежней партии, если `backfill` пропустил неизменившуюся историю. Текущий `updated_at` сверяется с последней успешной попыткой; расхождения требуют согласованной политики `sync`/`audit`.
5. Граница партии `created_since` сохранена как `recorded` или `attested` и равна `2023-01-01T00:00:00Z`; значение из `summarize` совпадает с БД.

Все пять условий проверяет ядро DDS (`run_from_stg_summary` → `load_dds`); задаче Airflow достаточно передать результат `summarize`.

Не передавайте DDS старую `verified` партию вместо неудачного текущего `batch_id`. `sample`, `legacy` и `unverified` не являются подтверждением полного охвата. Ограниченная выборка допустима для отдельной локальной разработки DDS, но её результат не публикуется как полный CDM. Текущие подтверждённые партии перечислены в [отчёте](../STG_FULL_LOAD_REPORT.md).

## Точка DDS → CDM и ошибки

Адаптер DDS принимает результат `summarize`, проверяет соответствие репозиториев, UUID и границы когорты в БД и публикует выбранные репозитории атомарно. Результат и исходные `batch_id` сохраняются в `dds.load_runs`, текущий запуск каждого репозитория — в `dds.repositories.current_run_id`. Только успешное завершение **всех требуемых DDS-партий** для выбранного среза открывает запуск CDM. `coverage_complete` сообщает о наличии публикаций всех трёх репозиториев; даты их исходных срезов могут различаться. CDM читает данные и `dds.publication_manifest` одной транзакцией, использует только `ready_for_cdm=true` и закрепляет набор парами «репозиторий — исходная партия», а не одним общим `run_id`. Правила показателей — в [памятке участнику 3](CDM_HANDOFF.md). Если DDS завершилась ошибкой, Airflow помечает эту задачу неуспешной, CDM не стартует, STG остаётся сохранённой для анализа и повтора.

CDM зависит от успешного DDS, а не напрямую от STG. Если CDM падает, DAG не считается успешным; сохранённые STG и подтверждённые DDS-данные остаются для повторного CDM. Публикуемый набор CDM должен меняться атомарно или по иному согласованному механизму, чтобы Metabase не увидела частичный пересчёт. Отдельный доступ Metabase к промежуточным STG/DDS не предусматривается.

DDS идентифицирует объекты по GitHub `repository_id`/`issue_id`/`event_id`, закрепляет вход по STG `batch_id` и сохраняет версию правил в журнале. Повтор не создаёт дубликатов событий и неизменившихся интервалов SCD2. Схема и проверки DDS определены в его контракте; стратегия публикации CDM остаётся частью участника 3.

## Доступ Metabase

BI должна запрашивать только подготовленные представления/таблицы схемы `cdm`. Текущий пользователь PostgreSQL `analytics` — администратор учебной базы и не является окончательной ролью BI. При интеграции CDM нужно создать отдельного пользователя с минимальными правами `USAGE` на `cdm` и `SELECT` на нужные объекты, а затем настроить подключение Metabase на эту роль. До готовности CDM конфигурация Metabase и существующие пароли остаются как есть.
