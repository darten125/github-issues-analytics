# CDM: витрины и словарь дашбордов

## Источник и зерно

CDM читает только DDS. Публикация возможна, когда в `dds.publication_manifest` есть все три ожидаемых репозитория с `ready_for_cdm=true`. Вход закрепляется парами `(repository_id, source_batch_id, current_run_id)` из одного снимка `REPEATABLE READ READ ONLY`. Для исторических графиков используется минимальный `last_complete_report_day` трёх репозиториев. Время и календарные даты трактуются в UTC.

| Объект | Зерно | Назначение |
| --- | --- | --- |
| `cdm.repository_snapshot` | Один репозиторий | Исходная партия DDS, собственный горизонт, общая последняя отчётная дата и время снимка |
| `cdm.issue_lifecycle` | Один `issue_id` | Создание, первое фактическое закрытие, первое повторное открытие, индивидуальный срок первого закрытия |
| `cdm.issue_day` | Пара `(issue_id, report_day)` | Состояние непосредственно перед следующей полуночью UTC, признаки событий к тому же срезу |
| `cdm.current_issue_label` | Пара `(issue_id, label_id)` | Метки текущего выбранного снимка Issue |
| `cdm.load_runs` | Один запуск CDM | Успех, повтор без изменений или ошибка |
| `cdm.current_state` | Единственная активная публикация | Отпечаток источника и общий горизонт для проверки свежести |

`issue_day` существует только от UTC-дня создания Issue до общего последнего полного дня включительно. Issue, созданный позже общего горизонта, остаётся в `issue_lifecycle` и текущих метках, но пока не входит в исторические графики. Последний открытый интервал DDS не экстраполируется за горизонт.

## Формулы

| График | Формула и смысл даты |
| --- | --- |
| Новые Issues по месяцам | Сумма `is_new` по UTC-дню создания; каждый Issue входит ровно один раз. Фильтр дат выбирает дни создания, поэтому крайние месяцы диапазона могут быть неполными. |
| Открытые на конец дня | Число Issues с `status_eod='open'` среди созданных к концу отчётного дня. Статус берётся из SCD2 DDS: `valid_from < cutoff` и `valid_to IS NULL OR valid_to >= cutoff`. |
| Доля закрытых | Число Issues с `status_eod='closed'` / число всех созданных к концу того же дня. При выборе нескольких репозиториев сначала суммируются числитель и знаменатель. |
| Время первого закрытия | Накопительная медиана индивидуальных сроков в днях среди Issues с первым фактическим переходом в `closed` до среза. Конверсия в Discussion включена; последующее открытие не исключает Issue. |
| Доля повторно открытых | Число Issues с фактическим переходом в `open` после закрытия / число когда-либо закрытых к одному срезу. При нулевом знаменателе результат `NULL`. |
| Первое закрытие по месяцам | Отдельная медиана сроков только тех Issues, которые впервые закрылись внутри выбранного UTC-месяца. Фильтр дат здесь относится к **дате первого закрытия**. |
| Текущие метки | `count(DISTINCT issue_id)` внутри каждой метки текущего снимка. Метки нескольких Issues и нескольких репозиториев суммируются без дублирования одного Issue внутри одной группы. Историческая дата к этому графику не применяется. |

Общие медианы всегда пересчитываются по индивидуальным срокам; медианы репозиториев не усредняются. Задачи без автора остаются в общих числах. Переход ровно в `00:00:00 UTC` относится к следующему дню.

## Дашборды и ограничения

- **Жизненный цикл Issues**: пять исторических графиков, фильтры по репозиторию и отчётной дате. По умолчанию выбранные репозитории объединяются; фильтр одного репозитория показывает его собственный ряд.
- **Первое закрытие по месяцам**: месячная медиана и фильтры по репозиторию и дате первого закрытия.
- **Текущие метки Issues**: число задач по меткам и таблица времени завершения исходной партии по каждому репозиторию; только фильтр репозитория.

Источник GitHub не предоставляет единый атомарный снимок всех Issues. `verified` подтверждает совпадение повторных проходов списка, но не абсолютную полноту истории API. Отчётные дни ограничены горизонтом DDS, а текущие метки и имена нельзя интерпретировать как исторические. Один Issue может иметь несколько меток, поэтому сумма столбцов меток обычно больше числа помеченных Issues. После частичного обновления репозитории могут иметь разную свежесть; исторические графики используют общий минимальный горизонт.

## Повторное развёртывание

1. Заполнить локальный `.env`, включая `CDM_READ_PASSWORD`, `METABASE_ADMIN_EMAIL`, `METABASE_ADMIN_PASSWORD` (не помещать секреты в Git).
2. Запустить Compose и полный DAG с `repository=all`, `mode=backfill`, `max_issues=null`, `full_load=true`. DAG сам вызывает STG → DDS → CDM. Для последующих ручных обновлений использовать `mode=sync` с теми же параметрами полного охвата.
3. Проверить `python -m src.cdm.cli validate` в контейнере Airflow.
4. Запустить с хоста `python3 scripts/provision_metabase.py`; повтор обновляет существующие источник, вопросы и дашборды без копий.

Сценарий использует обычный [HTTP API Metabase](https://www.metabase.com/articles/set-up-metabase-from-code-with-the-api), доступный и в свободной версии. Штатная сериализация YAML относится к платным редакциям.

Для приёмки в PostgreSQL выполните [CDM_DDS_RECONCILIATION.sql](sql/CDM_DDS_RECONCILIATION.sql) в одной транзакции `REPEATABLE READ READ ONLY`. Он сопоставляет партии, числа Issues, статус на общем последнем дне, фактические переходы и текущие связи меток, а затем показывает небольшой список Issues для ручного просмотра.

Для проверки без GitHub используйте только отдельную БД с именем на `_test` и фикстуру `src.dds.fixture`. Синтетический `sample` не публикуется в рабочую БД как полный CDM.
