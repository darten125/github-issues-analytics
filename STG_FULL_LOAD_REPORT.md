## Проверки качества и выявленная особенность

В `results/integrity_checks.csv` все 14 проверок дали 0: Issues до `2023-01-01T00:00:00Z`, Pull Requests, повторяющиеся ключи снимков, неверная структура/ID JSON, Issues без репозитория, один Issue ID в нескольких репозиториях, события без Issue с тем же `repository_id`, отсутствие или расхождение временной метки события. Для состава выборки использовались уникальные `issue_id`.

Сравнение последнего `state` с `closed_at` и последним известным статусным событием не выявило противоречий вида «открыт с `closed_at`» или «закрыт после последнего `reopened`». Есть **один закрытый Issue в NowInAndroid без события `closed`**. У него `state=closed`, заполнен `closed_at`, а в доступной истории есть `converted_to_discussion` вместе с другими событиями. Исходный JSON не менялся. DDS должен отдельно определить обработку этого перехода; полагаться только на `closed`/`reopened` для всех состояний нельзя. Агрегат сохранён в `results/state_anomalies.csv`.

`results/event_load_coverage.csv` подтверждает успешную загрузку истории для 493/493, 108/108 и 392/392 Issues. Незавершённых или неуспешных попыток в трёх партиях нет; у всех последних снимков Issue время `updated_at` совпадает со временем, зафиксированным при последней успешной загрузке событий.

Проверка сделана `2026-10-18 02:02:38–02:02:39 UTC`: Kotlin — 493, Ktor — 108, NowInAndroid — 392; `incomplete_results=false` для каждого ответа. Search API не использовался для самой выгрузки и не служит доказательством неизменности источника после проверки.

Перед запуском авторизованный `/rate_limit` показал 4 998 оставшихся запросов из 5 000. В `01:55:35 UTC` оставалось 4 454, после загрузки в `02:02:37 UTC` — 3 904; сброс основного лимита был указан GitHub как `02:20:53 UTC`. Отдельный Search API лимит при итоговой проверке составлял 30 запросов; заголовок после третьего проверочного запроса показывал 27. Исчерпания лимита, невосстановленных HTTP-ошибок и незавершённых партий не было. Клиент ограничивает ожидание повтора 120 секундами и число попыток тремя; необходимости возобновлять эту загрузку не возникло.

## Контракт источника для DDS

Проверены шесть read-only SQL-запросов в `quality_sql/dds_source_contract.sql`. Они показывают, как получить уникальные ID по репозиторию, последний наблюдавшийся JSON-снимок Issue, всю доступную историю уникальных событий Issue, отсортировать её по времени GitHub, выделить `closed`/`reopened`, проверить успешность и актуальность истории, а также отличить партию `sample` от `verified`. Запросы выполнены в PostgreSQL с подставленным существующим `issue_id`; исходные JSON-строки в пакет результатов не выгружались.

Примеры ключевых правил:

```sql
-- Один Issue может иметь несколько снимков и наблюдений.
SELECT repository_id, issue_id
FROM stg.issues_raw
GROUP BY repository_id, issue_id;

-- Последний наблюдавшийся снимок Issue.
SELECT DISTINCT ON (issue_id) issue_id, repository_id, raw_json, last_seen_at
FROM stg.issues_raw
ORDER BY issue_id, last_seen_at DESC, snapshot_id DESC;

-- История конкретного Issue: сначала один последний снимок на event_id,
-- затем порядок GitHub. В psql передать -v issue_id=<существующий ID>.
WITH latest AS (
    SELECT DISTINCT ON (event_id) event_id, issue_id, event_type,
           github_created_at, raw_json
    FROM stg.issue_events_raw
    WHERE issue_id = :issue_id
    ORDER BY event_id, last_seen_at DESC, snapshot_id DESC
)
SELECT * FROM latest ORDER BY github_created_at, event_id;
```

Для будущего SCD2 `created_at` Issue задаёт исходную границу, а статусные события — кандидатов на следующие границы интервалов `[valid_from, valid_to)`. События с одинаковым временем требуют детерминированного порядка по `event_id`; последний интервал остаётся открытым. Нужна сверка с последним `state`/`closed_at`, особенно для `converted_to_discussion`. Реализация DDS и SCD2 в эту работу не входила.
